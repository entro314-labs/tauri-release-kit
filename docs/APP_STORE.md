# App Store submission (macOS + iOS)

The kit's `app-store.yml` builds a Mac App Store `.pkg` and/or an iOS `.ipa`
and uploads them to App Store Connect. It is a **separate workflow from
release.yml**, and that separation is the whole design:

| | Direct download (`release.yml`) | App Store (`app-store.yml`) |
| --- | --- | --- |
| Certificate | Developer ID Application | Apple Distribution / 3rd Party Mac Developer |
| Installer signing | — (DMG is notarized) | 3rd Party Mac Developer **Installer** |
| Sandbox | optional | **required** |
| Provisioning profile | none | embedded, required |
| Notarization | required | not used (review replaces it) |
| Tauri updater | yes | must be off |
| Artifact | `.dmg` / `.app.tar.gz` | `.pkg` / `.ipa` |

Signing a direct-download build with an App Store certificate produces
something Gatekeeper distrusts. Submitting a Developer ID build to review gets
it rejected. They are two artifacts, and the kit keeps them two pipelines.

## Prerequisites

- A paid Apple Developer membership. The free tier cannot notarize or submit.
- A macOS machine for the one-time certificate export. Everything after is CI.
- Your app registered in [App Store Connect][asc-apps], with its **Bundle ID
  exactly equal** to `tauri.conf.json > identifier`.

## 1. Config files

Copy [`templates/appstore/`](../templates/appstore/) into `src-tauri/`:

```
src-tauri/tauri.appstore.conf.json     # App Store bundle overlay
src-tauri/Entitlements.appstore.plist  # App Sandbox + team identifiers
src-tauri/Info.plist                   # encryption declaration
```

Edit before submitting:

- **`bundle.category`** in the overlay — a real [Apple category][categories].
  A submission without one is rejected at validation.
- **`$TEAM_ID` and `$IDENTIFIER`** in the entitlements. `$IDENTIFIER` is
  `tauri.conf.json > identifier`; `$TEAM_ID` is the "App ID Prefix" shown on
  that identifier's page in the developer portal.
- **`ITSAppUsesNonExemptEncryption`** in `Info.plist`. `false` means "only
  encryption Apple exempts" — HTTPS is exempt. If your app encrypts anything
  itself, set `true` and file the annual self-classification report.

### Turn the updater off

Tauri has no config switch for this, so gate it in your own code — a Cargo
feature, or a flag your app reads at startup. A self-updating app violates
review guideline 2.4.5(iv), and the sandbox blocks the install anyway, so the
update prompt would only ever be a dead end for App Store users.

### Make the app actually work sandboxed

This is where most of the real work is, and it cannot be done from CI. Under
App Sandbox:

- File access outside the app container needs
  `com.apple.security.files.user-selected.read-write` and a real open/save
  panel — a path the user typed does not count.
- Network access needs `com.apple.security.network.client`.
- Spawning arbitrary subprocesses does not work.
- Anything writing outside `~/Library/Containers/<identifier>/` fails.

Add entitlements one at a time, for capabilities you can justify: each one is
a question you will be asked in review.

The pipeline asserts the sandbox entitlement made it into the signed bundle
before packaging, so a config that silently did not apply fails in CI rather
than in review.

## 2. Certificates

You need **two** for macOS, and they are different certificate types:

| Certificate | Signs | Secret |
| --- | --- | --- |
| Apple Distribution (or 3rd Party Mac Developer Application) | the `.app` | `APPLE_CERTIFICATE` |
| 3rd Party Mac Developer Installer (Mac Installer Distribution) | the `.pkg` | `APPLE_INSTALLER_CERTIFICATE` |

Create both in the developer portal's [Certificates][certs] page from a CSR
generated by Keychain Access, download and open them, then export each with
its private key:

```bash
# Keychain Access → My Certificates → right-click the entry → Export → .p12
openssl base64 -A -in AppleDistribution.p12 -out app-cert.txt
openssl base64 -A -in MacInstaller.p12      -out installer-cert.txt
```

Secrets: `APPLE_CERTIFICATE` + `APPLE_CERTIFICATE_PASSWORD`,
`APPLE_INSTALLER_CERTIFICATE` + `APPLE_INSTALLER_CERTIFICATE_PASSWORD`.

The workflow imports both into a throwaway keychain, auto-detects each
identity by certificate type, and tells you what it found. Override the
detection with `APPLE_SIGNING_IDENTITY` / `APPLE_INSTALLER_SIGNING_IDENTITY`
if you hold several.

If detection fails, the error names the exact problem — most often a
*Developer ID Application* certificate exported by mistake, which is the right
certificate for the other pipeline.

## 3. Provisioning profile

In [Identifiers][identifiers], create an App ID whose Bundle ID matches
`tauri.conf.json > identifier`. In [Profiles][profiles], create a **Mac App
Store Connect** profile for that App ID, linked to your distribution
certificate. Download it and:

```bash
openssl base64 -A -in profile-name.provisionprofile -out profile.txt
```

Secret: `APPLE_PROVISIONING_PROFILE`. The workflow writes it into the bundle
as `Contents/embedded.provisionprofile`. Without it, upload is rejected.

## 4. App Store Connect API key

`altool` authenticates only with an API key.

1. [App Store Connect → Users and Access → Integrations → Individual
   Keys][asc-keys], Add, name it, give it **Developer** access (iOS automatic
   signing needs **Admin**).
2. The **Issuer ID** is above the table → `APPLE_API_ISSUER`.
3. The **Key ID** is the row's first column → `APPLE_API_KEY_ID`.
4. Download the private key — **it can only be downloaded once**, and only
   after reloading the page.

```bash
openssl base64 -A -in AuthKey_ABC123.p8 -out api-key.txt   # → APPLE_API_KEY_BASE64
```

The workflow writes it back as `~/.private_keys/AuthKey_<KEY_ID>.p8`, which is
the filename and location `altool` searches for. That naming is not optional:
`altool` looks the key up by name, so a file called anything else is simply
not found.

Note the collision with `release.yml`: that workflow's notarization secret is
`APPLE_API_KEY` (the Key ID), while this one uses `APPLE_API_KEY_ID` for the
same value. Set both to the same string. They are separate names because
`APPLE_API_KEY` is what the Tauri bundler reads from the environment, and
overloading it here would be worse.

## 5. Wire up the workflow

```yaml
  app-store:
    needs: release
    uses: entro314-labs/tauri-release-kit/.github/workflows/app-store.yml@main
    with:
      project_path: 'apps/desktop'
      product_name: 'MyApp'        # productName exactly, including case
      macos: true
      ios: false
      validate_only: true          # ← start here
    secrets: inherit
```

**Start with `validate_only: true`.** It runs Apple's complete submission
checks — entitlements, provisioning profile, Info.plist, signature chain —
without consuming a build number or creating a TestFlight entry. Every
mistake in this document surfaces there, and you can iterate freely. Flip it
off when validation passes.

The `.pkg` is uploaded as a workflow artifact regardless of whether the upload
succeeded, so a failed upload never means rebuilding a universal binary.

## 6. iOS

Set `ios: true`. Two signing paths, chosen automatically by which secrets
exist:

**Automatic (recommended).** With only the API key present, Xcode manages
certificates and profiles, registering capabilities as needed. The API key
must have **Admin** access for this.

**Manual.** Set `IOS_CERTIFICATE`, `IOS_CERTIFICATE_PASSWORD` and
`IOS_MOBILE_PROVISION` (all base64) and Tauri imports them itself. Use an
Apple Distribution or iOS Distribution certificate and an "App Store Connect"
profile — a development certificate produces an IPA App Store Connect refuses.

Setting the certificate without the profile is a hard error; the two only work
together, and half a configuration silently falling back to automatic signing
would be much harder to debug than a failed step.

The workflow runs `tauri ios init` when `src-tauri/gen/apple` is not committed,
which is the normal case — it is generated, noisy in review, and rebuilt
identically each time.

### Bundle version

Tauri derives `CFBundleVersion` from `tauri.conf.json > version`. App Store
Connect refuses a build whose version it has already seen, so a resubmission
of the same app version needs a distinct bundle version:

```jsonc
{ "bundle": { "iOS": { "bundleVersion": "100" } } }
```

The same key exists under `macOS`.

### Icons

```bash
pnpm tauri icon /path/to/app-icon.png --ios-color '#fff'
```

iOS icons cannot have transparency, hence `--ios-color` for the background.

## Troubleshooting

**"No Apple Distribution / 3rd Party Mac Developer Application identity
found"** — you exported a Developer ID certificate. That one belongs to
`release.yml`.

**Upload rejected for a missing provisioning profile** — `APPLE_PROVISIONING_PROFILE`
is unset, or the profile is not a *Mac App Store Connect* profile, or its App
ID does not match `tauri.conf.json > identifier`.

**"app is not sandboxed"** from the pipeline — `bundle.macOS.entitlements` is
not pointing at your entitlements file in the *App Store* config overlay, or
the build did not sign (entitlements are applied at signing time, so an
unsigned build has none).

**The build signs but codesign shows a GUI prompt / the job hangs** — the
keychain's key partition list was not set. The workflow does this; a
hand-rolled keychain step usually does not.

**A build number is "already used"** — bump `bundle.macOS.bundleVersion` /
`bundle.iOS.bundleVersion`, or the app version.
